## Purpose

Multiple sources in this repository describe the same fields (counts, labels,
task verdicts, developer names). This document states the **ordered rule** used
to pick one authoritative value per field whenever two or more candidate values
compete. The rule was applied *before* writing `resolved_values.json`, and every
row in `conflict_resolution.csv` records the chosen flag according to this rule.

## Priority Rules (highest → lowest)

### SR-1 · Live-verified audit data beats everything else

**Applies to:** exact SHA counts, file counts, commit SHA, timestamp.  
**Rationale:** `readback_audit.md` (S1) was generated by mechanically comparing
`full_scope.csv` SHA values against the live Git tree. Every figure it cites
has a 0-mismatch verification stamp (`RESULT: PASS`). No other source performs
this level of verification.  
**Winner when invoked:** S1 then S2 then S3/S4 then S5/S6.

---

### SR-2 · Later authoritative snapshot supersedes earlier snapshot

**Applies to:** any verdict or membership decision that differs between the
intermediate finalpool (`mcpmark-eval-1031/BenchTasksCollv3@finalpool`,
committed 2026-03-23) and the canonical finalpool
(`bugmaker00/BenchTasksCollv3-review@finalpool`, committed 2026-04-09).  
**Rationale:** The canonical finalpool represents the final editorial decision.
The intermediate snapshot existed before editorial curation removed the 9 E3
tasks. A later, more-reviewed snapshot always supersedes an earlier one on the
same repository lineage.  
**Effect:** All 9 E3 tasks carry verdict `DROP` (not `KEEP`).  
**Winner when invoked:** canonical snapshot (S3/S4, boundary-review branch)
beats intermediate snapshot (S10).

---

### SR-3 · Structured machine-readable field beats narrative / derived label

**Applies to:** row-level labels in CSVs, explicit field values in JSON,
and developer identity.  
**Rationale:** A dedicated column or JSON field is unambiguous by design.
Narrative summaries (Issue #1) can paraphrase or abbreviate. Derived values
(dev name stripped from branch name) can be wrong when naming conventions vary.  
**Sub-rules:**
- The `source_dev` column in `boundary_review.csv` (S3) wins over any name
  derived from the `source_branch` column, because branch names follow three
  different suffix conventions (`-dev`, `_dev`, no suffix).
- The short `rule_label` value `"Passes all inclusion criteria"` in S3 is the
  canonical per-row label; the longer formulations in S4 and S5 are normative
  definitions, not row labels.  
**Winner when invoked:** S3 explicit field > S3 derived field > S5/S6 narrative.

---

### SR-4 · Active README beats base-template README, beats repository name

**Applies to:** project name.  
**Rationale:** `README.md` (S7) is the live user-facing document maintained
in every active working branch. `README_BASE.md` (S8) is a preserved historical
base template whose title reflects the v2 predecessor ("BenchTaskCollv2"). The
GitHub repository name (S9) encodes version and role (`BenchTasksCollv3-review`)
rather than a user-facing project title.  
**Winner when invoked:** S7 (`"MCPBench-Dev"`) > S8 (`"BenchTaskCollv2"`) > S9
(`"BenchTasksCollv3-review"`).

---

### SR-5 · "Kept tasks" is the authoritative scope for developer contribution counts

**Applies to:** `dev_task_count:*` fields.  
**Rationale:** Both Issue #1 (S5) and `readback_audit.md` (S1) explicitly cite
the **kept-only** count when listing developer contributions. The total-submitted
count (all rows in `boundary_review.csv` for a given developer) is available but
is not the cited metric for contribution tracking.  
**Winner when invoked:** kept-only count (S1 ∩ S3 KEEP rows) > total-submitted
count (all S3 rows).

## Notes

- When all sources agree on a numeric value (e.g., `total_candidates = 116`,
  `total_kept_e0 = 77`, `total_files_in_finalpool = 385`), the highest-priority
  source (SR-1) is cited as authoritative even though no conflict exists. This
  makes the source of truth explicit for future audits.
- Fields sourced from only one document (e.g., `finalpool_commit_sha` from
  `readback_audit.md`) are marked `single_source` in `conflict_resolution.csv`
  and require no rule application.
